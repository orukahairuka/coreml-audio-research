# 推論をメインスレッドの外で実行する実験

同期版の `prediction(from:)` は呼び出しの時間を短くするが、メインスレッド上で使うと画面の更新を妨げる（`e2e-optimization.md`）。そこで、推論をメインスレッドの外で実行したときの合成処理時間とメインスレッドの停止時間を実機で測った。

- 比較の基準（A）: 採用済みの 7 つの高速化（非同期の呼び出し、メインスレッド上）
- 条件: 条件 C、Release ビルド、4 入力×10 回。15 秒の空運転の後、A と B を交互に合成した
- メインスレッドの停止: メインキューで 2 ms ごとに動くタイマーの発火の間隔の、合成 1 回の中の最大値
- 生データ: `metrics/off_main_experiment_20261118/`（Git 管理外）
- 実装: `ThesisPipeline`（計測用の経路）のみ。通常の画面操作の経路（`AudioSynthesizer`）には入れていない

| 実験 | 実行場所 | 呼び出し |
|---|---|---|
| E1 | メインスレッドの外 | 非同期 |
| E2 | メインスレッドの外 | 同期 |
| E3 | メインスレッド上 | 同期 |

## 結果（B - A の中央値、n = 40）

| 端末 | 実験 | 合成処理時間の差 [ms]（95% 信頼区間） | モデルの呼び出しの差 [ms] | メインスレッドの最大の停止 A → B [ms] |
|---|---|---:|---:|---:|
| iPhone 13 | E1 | -4.6（-9.6〜+4.4） | +0.6 | 49.0 → 49.1 |
| | **E2** | **-208.9（-233.4〜-146.7）** | -201.1 | 51.4 → 43.7 |
| | E3 | -211.8（-257.7〜-168.6） | -207.5 | 50.3 → **133.7** |
| iPhone 17 Pro | E1 | -6.5（-8.9〜-4.2） | -3.6 | 19.8 → 19.9 |
| | **E2** | **-65.7（-79.0〜-58.6）** | -60.3 | 22.4 → 22.9 |
| | E3 | -86.8（-100.9〜-71.8） | -84.2 | 24.3 → **109.5** |

E2 の合成処理時間の中央値は、iPhone 13 で 1,544.3 → 1,331.1 ms、iPhone 17 Pro で 811.8 → 743.0 ms であった。すべての実験で、入力メル、Decoder の出力、HiFi-GAN の出力、波形の SHA-256 は A と B で一致した。

## 分かったこと

- 短縮の主な要因は、実行場所ではなく呼び出しの方法である。メインスレッドの外へ移すだけ（E1）では、ほとんど変わらなかった
- メインスレッド上の同期の呼び出し（E3）は、最大の停止が 2 台とも 100 ms を超えた
- メインスレッドの外の同期の呼び出し（E2）は、E3 と同程度に短縮しながら、最大の停止を基準と同程度に保った

## 限界

- 計測モードには画面の操作がない。メインスレッドの停止は、タイマーの間隔から求めた値であり、実際の画面の滑らかさを測ったものではない
- 実験ごとに熱状態が異なる（`nominal`〜`serious`）。A と B は交互に測っているが、実験の間で絶対値は比べない
- 条件 C のみ。他の条件の出力の一致と時間は未確認
- 同期版の呼び出しが短くなる理由は調べていない
