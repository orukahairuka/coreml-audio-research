# PyTorch 版と Core ML 版の Transformer Encoder・Decoder の同等性検証

モデル移植（PyTorch → Core ML）の妥当性の確認。音質の評価ではない。

## 方法

- スクリプト: [`scripts/verify_transformer_equivalence.py`](../../scripts/verify_transformer_equivalence.py)
- 生データ: `metrics/transformer_equivalence_20261118_003121/`（`summary.json` と入力ごとの `in<名前>_arrays.npz`。Git 管理外）
- 入力: iOS の計測モードが保存した Swift の前処理の正規化済みメル（`*_r0_mel_in.npy`、ch4-v4 の計測 `metrics/thesis_ch4v4_decinput_iPhone_3_20261118_001315/bulk`）。
  卒論第4章と同じ入力 1・2・6・11。PyTorch 版と Core ML 版に同じ配列を入れる（Swift と PyTorch の前処理の違いはこの検証に入らない）

| 入力 | T'（フレーム数） | メルの SHA-256（先頭） |
|---|---:|---|
| 1 | 262 | 35f61dbe027f |
| 2 | 137 | e7e0ecdf628b |
| 6 | 262（元は 292、Swift 側で 262 に切り詰め済み） | ad0fffd98daf |
| 11 | 185 | 339d4db44bf6 |

- PyTorch 版: `chkpt__20000.pth.tar`、Float32、CPU（`torch.set_num_threads(1)`）。torch 2.8.0
- Core ML 版: アプリに同梱の `Transformer_{Encoder,Decoder}_float32_fixed262.mlpackage`、`CPU_ONLY`。coremltools 9.0。
  **Mac（M4 Max）の CPU で実行**しており、iPhone の CPU ではない
- 比べる 3 種類
  - `pt_var`: PyTorch・可変長（T' フレームのまま。PronounSE の `synthesis.py` と同じ）
  - `pt_fix`: PyTorch・262 フレームに 0 埋め、pos は 1..262（iOS の EncoderRunner / DecoderRunner と同じ）
  - `ml_fix`: Core ML・固定 262（入力は `pt_fix` と同じ作り方）
- 指標: MAE、最大絶対誤差、コサイン類似度（配列を 1 列に並べて計算）
- 推論時（eval）のマスク: Encoder はマスクなし（0 埋めした行も全行が attention に参加する）。
  Decoder の self-attention は因果マスク（上三角）のみ、memory への dot-attention はマスクなし。Postnet は前後のフレームを見る畳み込み

### Decoder の比較

- **1 ステップ比較**: 全ステップ s で、`pt_var` の自己回帰で生成した同じ系列（先頭のゼロフレーム＋生成済み s フレーム）を入力し、
  そのステップで使う出力フレーム（`mel_out` の行 s）を比べる。差を次の 3 つに分ける
  1. Decoder 入力の 0 埋め: `pt_var` と「memory は可変長のまま、decoder_input だけ 262 に 0 埋め」
  2. Encoder 側の 0 埋め: 上の「decoder_input だけ 0 埋め」と `pt_fix`（memory も 0 埋めした Encoder の出力 262 行）
  3. 変換: `pt_fix` と `ml_fix`（memory も decoder_input も同じ配列）
- **自己回帰**: 3 種類をそれぞれ自分の出力を次の入力にして T' ステップ回す（`ml_fix` は Core ML の Encoder から通す）。
  各ステップの出力フレームと、最終ステップの Postnet 出力（先頭 T' 行。末尾 10 フレームは別に集計）を比べる

## 結果

### 1. Core ML への変換による差（`pt_fix` vs `ml_fix`）: 4 入力とも Float32 の丸め誤差の範囲

| 比較 | 入力 1 | 入力 2 | 入力 6 | 入力 11 |
|---|---|---|---|---|
| Encoder 出力 最大絶対誤差 / cos | 1.9e-5 / 1.0000000 | 1.4e-5 / 1.0000000 | 2.3e-5 / 1.0000000 | 2.6e-5 / 1.0000000 |
| Decoder 1 ステップ 最大絶対誤差 / cos 最小 | 3.6e-6 / 1.000000 | 2.6e-6 / 1.000000 | 3.1e-6 / 1.000000 | 3.0e-6 / 1.000000 |
| 自己回帰 全ステップの出力フレーム 最大絶対誤差 | 6.8e-5 | 9.6e-6 | 2.9e-5 | 1.7e-5 |
| 自己回帰 最終 Postnet 最大絶対誤差 / cos | 6.8e-5 / 1.0000000 | 9.6e-6 / 1.0000000 | 2.9e-5 / 1.0000000 | 1.7e-5 / 1.0000000 |

- 自己回帰で 137〜262 ステップ回しても、誤差は 1e-4 未満にとどまり、ステップを重ねても増え続ける傾向は見られなかった

### 2. 固定長化による差（`pt_var` vs `pt_fix`）: T' < 262 の入力でだけ大きい

| 比較 | 入力 1（T'=262） | 入力 6（T'=262） | 入力 2（T'=137） | 入力 11（T'=185） |
|---|---|---|---|---|
| Encoder 出力（先頭 T' 行） 最大絶対誤差 / cos | 0 / 1.0000000 | 0 / 1.0000000 | **8.09 / 0.102** | **8.69 / 0.152** |
| Decoder 1 ステップ: Decoder 入力の 0 埋め 最大絶対誤差 | 2.2e-6 | 2.7e-6 | 1.7e-6 | 2.0e-6 |
| Decoder 1 ステップ: Encoder 側の 0 埋め 最大絶対誤差 / cos 平均 | 0 / 1.000 | 0 / 1.000 | **0.50 / 0.924** | **0.46 / 0.949** |
| 自己回帰 出力フレーム cos 平均（最小） | 1.000（1.000） | 1.000（1.000） | **0.907（−0.132）** | **0.903（−0.086）** |
| 自己回帰 最終 Postnet cos（全体 / 末尾 10 以外 / 末尾 10） | 1.000 / 1.000 / 1.000 | 1.000 / 1.000 / 1.000 | **0.964 / 0.971 / 0.428** | **0.954 / 0.960 / 0.230** |

- T' = 262 の入力 1・6 は 0 埋めが起きないので、Encoder の出力は可変長と完全に一致した（比較手順の確認を兼ねる）。
  自己回帰の差（〜5e-5）は、入力の長さが違う行列計算の演算順による丸め誤差と考えられる
- **Decoder 入力の 0 埋め（未生成部分）は、全入力で 3e-6 未満**。因果マスクにより、未生成部分は出力に影響していない
- **差は Encoder 側の 0 埋めから生じている**。T' < 262 の入力 2・11 では、0 埋めした行が Encoder の attention に参加し、
  実フレームの行の Encoder 出力そのものが変わる（cos 0.10〜0.15）。Decoder はこの memory を参照するため、出力フレームも変わる
- 最終 Postnet の末尾 10 フレームは、入力 2・11 で特に差が大きい（cos 0.23〜0.43）
- 自己回帰の出力フレームのコサイン類似度は、ステップ 0 で低く出ている（0.35〜0.46）が、値自体が小さく最大絶対誤差は 2e-3 未満

### 3. 合計（`pt_var` vs `ml_fix`）

合計の差は、固定長化による差とほぼ同じ値になった（変換による差は 1e-4 未満で、合計にほとんど寄与しない）。

## 結論と限界

- Core ML（Float32・CPU）への変換は、同じ入力に対して PyTorch と Float32 の丸め誤差の範囲で一致する（4 入力、Encoder・Decoder・自己回帰・Postnet すべて）
- PyTorch 版の可変長と iOS 版の固定長の差は、変換ではなく **固定長化（262 フレームへの 0 埋め）による**。
  T' = 262 の入力では差は生じない。T' < 262 の入力では、Encoder がマスクなしで 0 埋め部分を参照するため、出力が変わる
- 固定長化の差のうち「実フレームの Encoder 出力が変わる効果」と「Decoder が 0 埋め部分の memory 行を参照する効果」は、
  今回の比較では分けていない（どちらも Encoder 側の 0 埋めとしてまとめて測った）
- 長さが 262 を超える入力（入力 6 の元の 292 フレーム）を切り詰める影響は、両者に同じ 262 フレームを入れているので含まない
- Core ML 版は Mac の CPU で実行した。iPhone の CPU・GPU・Neural Engine、Float16・Int8 のモデルは対象外
- これはモデル出力の数値の比較であり、合成音の聴感上の品質を示すものではない
